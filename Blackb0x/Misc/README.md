# Blackb0x/Misc

Now that `Blackb0x/ramdisk/` has been deleted outright (see
`.claude/LEGACY_FLOW.md`/`.claude/NEO_FLOW.md`), this directory is where
everything from it worth keeping for provenance/reference lives instead —
plus the one original source tarball still needed going forward
(`tihmstar-untether.tar`; every other original tarball was dropped — see
"Original tarballs" below, including `RamdiskBins.tar`, now unpacked into
`bin/`).

- `rc.boot` — **deleted**. This was the restore ramdisk's early-boot
  script (behavior doc in `.claude/LEGACY_FLOW.md`), kept here on the
  assumption `bakeRamdisk()` would need to re-splice it. That assumption
  didn't hold: the entrypoint splice target ended up being `/sbin/launchd`
  (see docs/HISTORY.md's "Entrypoint injection point" entry), never
  `/etc/rc.boot` at all in the current design, so there was nothing left
  for this file to feed. Recovered its actual content once (from
  `Blackb0x/Files/ssh.tar` in commit `85e2d8b`, before deleting it for
  real) to check for logic the current entrypoint might be missing — it
  turned out to be `msftguy/ssh-rd`'s own rc.boot, not something written
  for this project at all: remounting the ramdisk rw, freeing RAM by
  deleting bundled firmware update blobs, disabling `/sbin/reboot` so its
  rescue shell can't be killed, starting `sshd` on the ramdisk itself (the
  same early-SSH-bootstrap approach already investigated and rejected
  elsewhere in this file), and finally chaining into Apple's own real
  `restored_external`/`restored_update`/`restored`/`ramrod` — genuine
  NAND-reflashing daemons, which this project must *not* invoke (a
  jailbreak persists files onto the already-installed OS; it doesn't
  reflash it). The one real gap found: `nvram auto-boot=1`, which
  SecureROM/iBoot apparently clears once a real DFU payload has run — now
  ported into `entrypoint.c`'s own `set_auto_boot()`, called right before
  every `reboot(2)`.
- No `sshtar/` here anymore. `msftguy/ssh-rd` (the `third_party/ssh-rd`
  submodule, symlinked in as `Misc/sshtar` for one session) was
  investigated as the real, confirmed source of the raw SSH-bootstrap set
  the original disassembled binary staged (`bash`, `ls`, `sh`, `sshd`,
  `scp`, `sftp-server`, `mount.sh`, `mktar.sh`, `device_infos`, 4 of 5
  needed dylibs) — a byte-for-byte match, verified by downloading and
  checking a couple of these directly. But that whole set turned out to be
  `ssh-rd`'s own "Automated SSH ramdisk creator/loader" tool: a *rescue SSH
  shell that runs during the ramdisk-boot stage itself* (its own
  `mount.sh` does exactly what `entrypoint.c` already does directly via
  raw `mount()` syscalls), entirely separate in purpose and timing from
  the real `openssh` package `postinstall.sh` installs onto the fully-booted
  device afterward — and `entrypoint.c` never spawns/execs anything to
  begin with, so staging these binaries alone would never have started a
  session even if wired in. NEO_FLOW doesn't need a ramdisk-stage rescue
  shell, so `third_party/ssh-rd` was removed entirely (submodule
  deregistered, `.gitmodules` entry gone) rather than left unused.

## `picklist.txt` (not checked in here — see below)

Machine-generated by `scripts/build_deb_cache.py`, but **not** written
anywhere in this repo, including this directory — it and its
`Packages`/`Packages.gz` companion are pure build-time artifacts now,
generated into a temp directory that `bakeRamdisk()`
(`Blackb0x/Source/BakeRamdisk.cpp`, the actual "ramdisk build program")
owns and shells out to `build_deb_cache.py --output-dir <tempdir>` to
populate, every time a ramdisk gets baked. Documented here anyway since
this is where its provenance/behavior is explained. It's the resolved
output of running `Blackb0x/Misc/packages.txt` (a flat package-name list)
through real `apt` dependency resolution against this project's own
`*.list` sources: the exact, deduplicated set of `.deb` filenames under
`Blackb0x/Debs/` that actually get copied into the ramdisk overlay's
`files/debs/` — not the whole (append-only, never-pruned) `Blackb0x/Debs/`
directory, which accumulates every version ever fetched.

Running it against the current `packages.txt` resolves all but two names.
`com.ih8sn0w-squiffy-winocm.p0sixspwn` genuinely can't resolve through apt
at all — its `Depends: firmware (>= 6.1.3), firmware (< 7.0)` only matches
a 6.1.4 device, and this project's sandboxed resolution declares its
synthetic "firmware" version as `8.4.2` (see the script's own comment for
why: it can't satisfy every firmware range this ecosystem has ever used in
one resolution pass, so it picks this project's newest/most-capable
supported target). This isn't a bug — per `.claude/NEO_FLOW.md`, per-branch
persistence payloads like this one are meant to be installed as direct
loose-file copies, not resolved through apt at all, so dropping out of this
list here is the correct signal, not a gap to fix. `essential` also still
doesn't resolve, genuinely not found in any of the five configured repos
today, despite `Blackb0x/Debs/essential_0-1_iphoneos-arm.deb` already
existing here from some earlier, no-longer-reachable source.

`bigboss`, `modmyifone`, `saurik`, `zodttd` used to be in `packages.txt`
too, and used to show up in every single resolution run as "no
installation candidate" warnings — confirmed, directly against a real
bake run, to be permanently dead: these are sources.list.d *basenames*
that leaked into `packages.txt` as if they were real package names during
the original dependency-graph scrape (see `docs/HISTORY.md`), not
temporarily-unavailable packages. Removed outright rather than left to
warn on every future build forever.

## `bin/` — gone entirely now (was: the ramdisk-stage tool set, unpacked from `RamdiskBins.tar`)

Originally `dirhelper`, `gzip`, `libiconv.2.dylib`, `plutil`, `sleepcmd`,
`tar`, `uname`, `untar` — flat, matching this directory's existing
convention, dropping the original tarball's `usr/bin/`/`usr/lib/`
structure (the AppleDouble `._*` resource-fork sidecar files tar carried
alongside several of these were also dropped — pure macOS metadata, never
used on device). `dirhelper` no longer lives here — moved up to
`Misc/dirhelper` directly once its real nature turned up (see that
section below); it was only ever miscategorized as part of "the
ramdisk-stage tool set" by virtue of sharing a tarball with the genuine
utilities, not because it is one.

`gzip`, `tar`, `uname`, and `sleepcmd` were later deleted outright (not
just left unreferenced) once nothing staged them into the ramdisk at
all — every real Cydia package the jailbreak actually installs already
covers the same functionality, confirmed directly against each vendored
`.deb`'s own payload, not assumed: `gzip_1.6-7_iphoneos-arm.deb` ships
`./bin/gzip`, `tar_1.29-10_iphoneos-arm.deb` ships `./bin/tar` and
`./usr/bin/tar` (and `tar` is a direct `packages.txt` entry, not merely
transitive), and `coreutils-bin_8.12-9_iphoneos-arm.deb` ships both
`./bin/uname` and `./bin/sleep` — the latter functionally identical to
`sleepcmd` (confirmed via `strings`/disassembly: `sleepcmd` is a trivial
wrapper around libSystem's own `sleep()`, and is armv7/arm64-only besides,
so it couldn't even run on the armv6-only AppleTV2,1). `untar` was deleted
too, for a different reason — see its own paragraph below.

`plutil` was deleted later still, once a real source turned up after all:
this file's own earlier claim that "no package in any of this project's
three configured repos ships it" was true as far as it went, but nobody
had checked BigBoss's `com.ericasadun.utilities` specifically — a real,
still-live, dependency-free package (no Depends:, no postinst/preinst at
all) that ships `./usr/bin/plutil`, confirmed MD5-identical byte-for-byte
to this checked-in copy (`16dc1bc39e4d3f8c6bf9f9f537722587`) against the
live repo's own index, not assumed. Added to `packages.txt` directly.

`libiconv.2.dylib` was deleted last, and `bin/` along with it (nothing
left once it was gone) — not because a package covers it like the others
above, but because it never needed a package in the first place. Its own
embedded SCCS "what" string gives it away directly:
`@(#)PROGRAM:iconv.2  PROJECT:libiconv-35` — Apple's own real
`opensource.apple.com` project-naming convention, not a jailbreak-
community binary at all. Confirmed by downloading the actual source:
`https://opensource.apple.com/tarballs/libiconv/libiconv-35.tar.gz`
(HTTP 200, a real Xcode-project-wrapped build of upstream GNU libiconv —
its own `libiconv.plist` build manifest reports `OpenSourceVersion: 1.11`,
a real GNU libiconv release), also mirrored officially on GitHub at
`apple-oss-distributions/libiconv`. `/usr/lib/libiconv.2.dylib` is a core
Darwin system library Apple bakes into the base OS on every iOS/tvOS
device at the factory, the same as `libSystem.B.dylib` — unlike
`gzip`/`tar`/`uname`/`sleepcmd`/`plutil` above (real gaps in a stock
retail OS that a Cydia package then filled), this one was never actually
missing from a real device in the first place, so there was never
anything for a package to provide.

**`ldid` and `otool` deliberately excluded**: the real `ldid` .deb
(`Blackb0x/Debs/ldid_1.2.1_iphoneos-arm.deb`, already in
`packages.txt`) provides `ldid`, and saurik's `odcctools` package
(confirmed by extracting `odcctools_286-8_iphoneos-arm.deb` directly from
`apt.saurik.com` — real `./usr/bin/otool` inside) provides `otool` — added
to `packages.txt`, not yet fetched into `Blackb0x/Debs/` (that happens
automatically, the next time `scripts/build_deb_cache.py` runs, the same as
any other name added there). Nothing needs a raw copy of either before
`postinstall.sh` gets a chance to install the real packages — see
`.claude/NEO_FLOW.md`. `plutil` itself is gone now — see
the `bin/` section above for `com.ericasadun.utilities`, the real BigBoss
package that turned out to ship it (confirmed only by checking that repo
specifically; the earlier "no package in any of this project's three
configured repos ships it" claim, from downloading and inspecting all
~550 of saurik/awkwardtv/this fork's own packages directly, was accurate
as far as it checked — BigBoss just wasn't one of the three at the time).

`untar` was deleted too, on different grounds than the four above: nothing
in this codebase — not `entrypoint.c`, not `postinstall.sh`, not any
script — ever referenced it by name, and unlike `gzip`/`tar`/`uname`/
`sleepcmd`, no vendored package ships anything by that name either, so
there was no real replacement to point to — it was simply genuine dead
weight. Real `tar` (the real package now installed by the jailbreak)
already handles extraction itself (`tar -x`), which is normally all
"untarring" needs; a *separate* `untar` binary alongside it suggests it
was either a narrower-purpose tool (e.g. hardcoded to a fixed extraction
root, no flags) or leftover cruft from whatever originally assembled
`RamdiskBins.tar` — never conclusively determined which, but moot either
way once nothing referenced it.

## `dirhelper` — not a utility, promoted out of `bin/`

Lives at `Misc/dirhelper` directly now, not `Misc/bin/dirhelper` — it was
only ever sitting in `bin/` by accident of packaging (bundled inside the
same `RamdiskBins.tar` as the real command-line utilities above), not
because it is one. It's the file `entrypoint.c`'s `install_ios7_dirhelper()`
reads and its only consumer swaps into `/usr/libexec/dirhelper` as the
iOS7/8.x-(non-8.4) persistence exploit itself — real Apple/Cydia code
never touches that path at all. Don't confuse it with `p0sixspwn`'s own,
entirely separate `dirhelper` payload
(`Blackb0x/Debs/com.ih8sn0w-squiffy-winocm.p0sixspwn`'s own
`usr/libexec/dirhelper`, installed via a different call for the 6.1.4
branch — confirmed genuinely different files, not the same binary shared
by coincidence: a real 50KB Mach-O vs. p0sixspwn's own 262-byte bash
script, different hashes).

**What it actually does** (reconstructed directly from its own strings and
symbol table — `main`/`remount`/`tar`/`run`/`file_exists` — no source was
ever found, see below): remounts `/` via `/sbin/mount / rw,suid,dev`,
self-tests by creating and deleting a throwaway `/rwtest` file, checks
`/usr/share/terminfo/x/xterm-xi` as a proxy marker for "is Cydia already
installed", and if not, extracts a bundled `/private/var/Cydia.tar` using
its own accompanying `/private/var/tar` binary (`posix_spawn`,
`--no-overwrite-dir`) — a self-contained Cydia bootstrap independent of
any real package manager. It finishes by running every script under
`/etc/rc.d/` (a generic post-boot hook). Watermarked "iH8sn0w is here
dawg!" in its own string table. Since real `/usr/libexec/dirhelper` is a
legitimate daemon the OS invokes automatically and repeatedly with root
privilege, replacing it makes iOS/tvOS unknowingly re-run this whole flow
— the actual persistence mechanism for a firmware generation with no
other untether (`.claude/LEGACY_FLOW.md`: "genuinely tethered, no
untether exists for this range at all").

**Where it came from: the ether.** Extensively searched and could not
find this binary's source, or even a second copy of it, anywhere:

- Confirmed present, byte-identical (`3fa84e1019032ac26829228cf05cd0ee815ffb2d`
  git blob hash), in the original upstream `NSSpiral/Blackb0x` repo at
  `Blackb0x/Files/dirhelper` since its very first commit (`85e2d8b`,
  "Initial Commit" — no message, no context). A real user's debug log
  on that repo's issue tracker (#68) shows it being extracted at runtime
  from `Contents/Resources/RamdiskBins.tar` inside the original macOS
  `Blackb0x.app`, alongside `libiconv.2.dylib`/`plutil`/`untar`/`uname`/
  `gzip`/`otool`/`ldid`/`sleepcmd`/`tar` — a flat grab-bag of ARM
  binaries the original developer(s) assembled themselves, with zero
  provenance recorded for any individual file in it.
- Zero results, for every one of five distinctive strings from this
  binary, across GitHub's entire code-search index (`"RootFS Successfully
  remounted as READ WRITE"`, `"iH8sn0w is here dawg"`, `"Cydia is still
  installing"`, `"Cydia should now be installed"`, `"Why does this rwTest
  exist"`) — the source was never checked into any public repo GitHub can
  see.
- Not present in any of iH8sn0w's own 26 public repos (`github.com/iH8sn0w`),
  including `iBooty` (his own tethered-boot tool for this same
  limera1n/A4 hardware family) or his `sn0wbreeze`/`xpwn` forks.
- Directly compared against `firecore/Seas0nPass`'s real `saffron`
  untether payload (`bundles/AppleTV2,1_4.3_8F455.bundle/saffron.tgz`'s
  `./boot/untether`) on the theory that AppleTV's other major
  `dirhelper`-hijacking tool might share code — it doesn't: different
  architecture (armv6 `PREBOUND` vs. our armv7 `PIE`), different size
  (8,192 vs. 50,240 bytes), zero shared strings, and fundamentally
  different content (`saffron`'s is a low-level IOKit/ROP kernel
  re-exploitation payload; ours is a high-level userspace installer).
  Also confirmed Seas0nPass never shipped anything for AppleTV3,x or past
  6.2.1 firmware at all, ruling it out as a source on device/firmware
  grounds alone.
- The *technique* — not the binary — traces cleanly to **evasi0n6**
  (`OpenJailbreak/evasi0n6`, the real archived source of evad3rs' iOS
  6.0–6.1.2 untethered jailbreak, Oct 2012). Their real Cydia package
  (`com.evad3rs.evasi0n`) installs exactly `/usr/libexec/dirhelper`
  (`untether/package.sh`: `cp ../kernel/extras/dirhelper
  package/usr/libexec/dirhelper`), and their `jailbreakinstaller.m`'s
  `prepare_jailbreak_install()` contains
  `run((char *[]) {"/sbin/mount", "-u", "-o", "rw,suid,dev", "/", NULL},
  NULL)` — the exact same mount flags in the exact same order as this
  binary's own `remount()`, built on the same `posix_spawn`+`waitpid`
  `run()`-helper pattern this binary's own imports match, bootstrapping
  Cydia from a bundled archive (`kernel/Cydia.tar.lzma`) the same way
  ours does from `/private/var/Cydia.tar`. But even evasi0n6's own team
  never published *their* dirhelper's source either — their Makefile
  just does `cp dirhelper $(TEMPDIR)/usr/libexec/dirhelper` from a
  pre-built file, and that exact file is now a broken symlink
  (`../../kiki/ddi/dirhelper`, target missing) even in their own archived
  repo.

Best real conclusion: this is almost certainly someone's (plausibly
iH8sn0w's, given the watermark, who was active and cross-connected across
this exact scene) adaptation of evasi0n6's well-documented "hijack
`dirhelper`, remount `rw,suid,dev`, bootstrap Cydia from a bundled
archive" technique to the AppleTV/DFU-restore context — but the compiled
binary itself was never open-sourced by anyone at any point, the same way
the very team that invented the technique never open-sourced theirs. Not
recoverable by more searching; this is the actual, fully-investigated
answer, not a gap in the investigation.

## etasonATV / tihmstar-untether provenance

`Blackb0x/ramdisk/files/etasonATV/` is tihmstar's EtasonATV untether payload
(the first public AppleTV 3 jailbreak, targeting AppleTV3,1/3,2 on firmware
7.4/12H876 and 7.5/12H885), delivered live via a DNS-hijack + Trailers-app
WebKit exploit chain (see https://etasonatv.tihmstar.net/). Blackb0x's
ramdisk-stage `sbin/launchd` installer copies these files onto the target
volume directly, selecting them for its "iOS 8.4 untether" branch — it never
needed tihmstar's live delivery chain, since Blackb0x already has root
filesystem access via the DFU/checkm8 restore-ramdisk path.

We tried to independently verify/re-source this payload against tihmstar's
live infrastructure and failed:

- `46.166.144.59` (the original DNS-hijack IP tihmstar tweeted) is dead —
  no DNS response, ports 80/443 both closed.
- `188.166.193.52` (the current DNS-hijack IP) is alive and still nginx-vhost
  aware for `Host: trailers.apple.com` — it 301s to
  `https://etasonatv.tihmstar.net` instead of serving exploit content
  directly. Without that Host header it falls through to an unrelated
  default vhost (a "doubleH3lix" jailbreak landing page).
- DNS resolution *through* that IP (`dig trailers.apple.com @188.166.193.52`)
  returns a malformed EDNS-only response with no actual answer — the
  DNS-hijack step itself looks non-functional today, even though the HTTP
  layer behind it is still configured.
- The profile certificate path named in the site's own instructions,
  `trailers.apple.com/whyIsThisFileNameSoLong.cer`, returns a 500 on
  `etasonatv.tihmstar.net` directly (an nginx location still exists for it,
  but whatever backend generates the cert is broken) rather than a 404.
- `untether.deb`, `expl.js`, `exploit.js`, `etason.js`, and every other
  filename we guessed all came back clean 404s. Even the site's own embedded
  screenshots (`images/instructions/step1.JPG`, etc.) 404 — the page itself
  admits "a few images are missing."

Conclusion: there is no live, independently-downloadable copy of this
payload anywhere. It was only ever distributed in-band during a live
exploit run, never hosted as a static artifact. The copy checked into this
repo (originally `Blackb0x/Files/tihmstar-untether.tar`, byte-identical
across every Blackb0x fork we checked) is almost certainly one of the only
surviving standalone copies, and is kept as-is rather than re-derived.

### The `jsc`/`rtbuddyd`/`--early-boot` mechanism, resolved

`entrypoint/`'s reverse-engineering (see that directory's own README) turned
up two things the disassembly alone couldn't explain: a symlink aliasing
`jsc` (JavaScriptCore's CLI interpreter) as `rtbuddyd`, and a second symlink
from `expl.js` to a file literally named `/--early-boot`. Resolved via
tihmstar's own conference talk on this exact exploit chain ("Jailbreaking
the AppleTV 3 — Tales from a full stack hack", see the link in
`AGENTS.md`'s External references):

- `rtbuddyd` is a normal Apple daemon launchd auto-starts at early boot,
  invoked as `rtbuddyd --early-boot`.
- The untether replaces the on-disk `rtbuddyd` binary with Apple's own
  `jsc` — still validly signed, so it passes code-signing checks that would
  block an unsigned or patched binary outright.
- `jsc` treats its argument as a script path to open and execute. So
  launchd's `rtbuddyd --early-boot` invocation actually runs `jsc
  --early-boot`, and `jsc` resolves that as the file `/--early-boot`,
  follows the symlink to `expl.js`, and executes it as JavaScript.

There's no OS-level boot-arg mechanism involved at all — `/--early-boot` is
just the accidental file path that falls out of `jsc`'s own argv-handling
once it's substituted in for a daemon that's always started with that
particular flag. `expl.js` is the WebKit/JSC exploit itself, so this
sequence re-establishes kernel R/W and re-applies the kernel patches fresh
on every single boot — the entire untether, with zero genuine kernel/launchd
support for persistence, just a clever abuse of one daemon's calling
convention.

## `sbin/launchd` — source and pinned paths

`Blackb0x/ramdisk/sbin/launchd` is not Apple's launchd — it's a precompiled
ARMv6 Mach-O that replaces PID 1 on the ramdisk just long enough to lay the
jailbreak payload onto the real filesystem, then hands off to the real
launchd. Its own strings self-identify it: `blackb0x Jailbreak - by
@NSSpiral`. No source for it exists anywhere we could find — not in
NSSpiral/Blackb0x itself (bundled only as an opaque Xcode resource, loaded
via `[[NSBundle mainBundle] pathForResource:@"launchd" ofType:@""]` in the
original `Patcher.mm`), not in any of its ~30 GitHub forks, not in NSSpiral's
other public repos, and it doesn't turn up in a GitHub-wide code search for
its own distinctive strings (`"Installing etasonATV"`,
`"Installing blackb0x tether"`, `"Cloning directory"`). It was most likely
hand-built once and never had its own build recipe committed anywhere.

Everything below was recovered by disassembling its embedded strings
(`strings Blackb0x/ramdisk/sbin/launchd`) — this is the ground truth for
what the binary reads off the ramdisk's `/files/` tree at boot, independent
of anything `postinstall.sh` or the new C++ code does later:

- Loose top-level files: `.blackb0x`, `com.blackb0x.postinstall.plist`,
  `com.openssh.sshd.plist`, `fstab.atv` (gutted — its two lines only
  duplicated the entrypoint's own hardcoded `mount()` calls for
  `/dev/disk0s1s1`/`/dev/disk0s1s2`, and it was only ever installed by the
  6.1.4/`p0sixspwn` branch — nothing left worth keeping), `joshtv.list`,
  `kodi.png`, `nito.png`, `profile`, `pubkey.key`, `rtbuddyd.bin`,
  `postinstall.sh`, `xbmc.list`.
- `files/cydia/` — walked recursively (`bin/`, `sbin/`, `usr/{bin,sbin,lib,

  `usr/libexec/{ssh-keysign,sshd-keygen-wrapper}`, `usr/include/db{,_cxx}.h`,
  `usr/lib/apr.exp`, `usr/lib/dpkg/methods/apt/{desc.apt,names}`,

The binary does an exact filename match before it will move a `.deb` into
place — it doesn't glob or fuzzy-match. Comparing its 8 pinned filenames
against what's actually in `Blackb0x/Debs/` today:

| `beigelist_2.2.6-30_iphoneos-arm.deb` | same | yes, exact match |
| `com.nito.updatebegone_0.2-1_iphoneos-arm.deb` | same | yes, exact match |

### Which deb this reveals we still need

This binary force-installs `sqlite3-dylib` and `sqlite3-lib` directly by
name — it doesn't rely on apt pulling them in as a dependency of something
else. `sqlite3-dylib` is fine either way (it's still a real dependency of
another root package, so it'd get pulled in regardless). **`sqlite3-lib` is
not** — nothing in this project's dependency graph formally depends on it,
which is exactly why an earlier graph-based trim dropped it from what was
then `persist_packages.txt` (since merged with the former
`ramdisk_packages.txt` into `Blackb0x/Misc/packages.txt`). But this binary
explicitly installing it by name, before dpkg dependency resolution is even
in the picture, means it's still a load-bearing package, not dead weight
the graph missed correctly — it's back in `packages.txt` now, but the
graph-based approach alone would have dropped it again on "no known
dependent" grounds if this hadn't been caught here first.
